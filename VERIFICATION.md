# Результаты проверки

Проверено 16 октября 2026 года на Windows, .NET SDK 10.0.401, runtime .NET 9.0.20 и Docker Engine 29.6.2. Целевая платформа приложения и тестов — net9.0. Dockerfile собирает приложение SDK .NET 9 и запускает на ASP.NET Core 9.

## Автоматические проверки

```sh
dotnet test TaskApi.sln -c Release
dotnet tool restore
dotnet ef migrations has-pending-model-changes --project src/TaskApi --no-build --configuration Release
```

Полный набор автоматических тестов: **27 пройдено, 0 ошибок, 0 пропущено**. Тесты запущены с настоящими PostgreSQL 17 и RabbitMQ 4.1 в отдельных контейнерах Testcontainers.

Проверяются:

- Создание, значения по умолчанию, серверные даты и валидация Title, Priority и Guid.
- GET всех задач и физическое удаление записи из PostgreSQL.
- Сохранение завершения перед публикацией и отсутствие события при сбое БД.
- Получение реального JSON-события RabbitMQ с ожидаемыми полями, exchange и routing key.
- Одновременное завершение одной версии xmin: один ответ 200, один 409 и одно событие.
- Повторное завершение без изменения CompletedAt и без нового события.
- Работа при недоступном брокере, логирование события и переполнение очереди.
- Ожидание публикаций при остановке, отмена зависшей отправки и закрытие транспорта.
- Принудительное закрытие сокетов при игнорировании отмены клиентом RabbitMQ, включая проверку с приостановленным реальным брокером.
- Повторное объявление exchange после неудачной инициализации.

## Проверка Docker Compose через HTTP

Текущий Dockerfile собран в отдельном Compose-проекте с новым томом PostgreSQL и случайными портами на loopback. **37 проверок пройдено**.

Через реальные HTTP-запросы проверены создание, значения по умолчанию, валидация, список, завершение, повторное завершение и удаление. Состояние и физическое удаление дополнительно проверены прямым чтением PostgreSQL. Через RabbitMQ Management API получено фактическое событие; его поля и время совпали с HTTP-ответом и сохранённой записью. Параллельные HTTP-запросы дали 200 и 409, с одним событием.

При остановленном RabbitMQ завершение вернуло 200 за 16 мс, осталось сохранённым в PostgreSQL, а полный JSON события попал в лог. После запуска брокера публикация восстановилась. При SIGTERM API завершился с кодом 0 за 0,875 секунды; принятое перед остановкой событие было получено из RabbitMQ.

Тестовые контейнеры, сеть, том БД и образ приложения удалены. Исходники в ходе HTTP-прогона не менялись.

## Границы решения

Доставка RabbitMQ работает в режиме best effort, предусмотренном заданием. Нет outbox, publisher confirms и повторной доставки; аварийное завершение процесса может потерять события из памяти. Ограничения описаны в README.
